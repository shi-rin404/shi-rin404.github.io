Detailed

Mesh Importer/Exporter

Other people had already reverse-engineered much of the game's mesh format. I reverse-engineered three parts of the format:

  • Bone-based collider cylinders. IDVMI-Tools generates custom colliders in the game's binary format on export. See Collider View ·
  • LOD data. I identified the table's position and length. My tool keeps the raw data on import and writes it back on export.
  • Bone usage bitmask. The engine uses this mask to optimize which bones it processes. IDVMI-Tools builds the mask on export, so I can enable bones without copying the mask from an original mesh.

The biggest challenge for me was converting the game's 4×4 bone matrices. The game stores its rest transforms in row-major order. I transpose the source matrices, convert them into Blender's coordinate system, and apply a separate correction for Blender's edit-bone axes.

Animation Importer/Exporter

I decoded most of the animation format, except for a suspected checksum field and the purpose of several fields provisionally labeled as position, rotation, and scale keys.

Each packed quaternion is a little-endian 32-bit word. From the most significant bits to the least significant:

  • 2 bits for the An index from 0 to 3 that identifies the omitted component (X, Y, Z, or W). The decoder reconstructs it from the unit quaternion norm.
  • 10 bits each for components C, B, and A, in that order

I decode each stored component from its 10-bit integer value c using:

\[v = \frac{2(c/1023)-1}{\sqrt{2}}\]

The decoder reconstructs the omitted component using the unit quaternion norm. It assigns A, B, and C in reverse cyclic order through X, Y, Z, and W, starting immediately before the omitted component. For example, if the selector omits Y, then A maps to X, B to W, and C to Z.

Asset Lookup

I disassembled the game's engine DLL using A tool for inspecting and modifying the memory of a running program. and IDA, picked a virtual asset path, and traced it backward. I found that the engine hashes the path with seeded XXH32, even though the archives use 128-bit hashes.

Searching the DLL for strings led me to the lookup file. It maps the 32-bit key to a descriptor containing the 128-bit hash and uses a fallback seed for keys listed in the collision table.

I worked out the lookup logic and gave my pseudocode to AI to implement the and functions.

I integrated my asset lookup implementation with the asset extraction code from NeoXtractor.

Prefab Binary Converter

I had my own copies of the game's legacy XML prefabs. When the game switched to a new engine, it started using a binary XML format.

People in the modding community. spent a while editing the new prefab files in a hex editor and loading them into the game. Seeing how those edits changed the game gave me clues about what some of the key fields did and helped me reverse-engineer the format.

The first challenge was recognizing LEB128. I hadn't encountered it before, and its variable-length encoding made it harder to tell where one value ended and the next began.

The second challenge was recognizing that the XML hierarchy was stored in Breadth-first search visits nodes one level at a time, starting from the root in a tree. order. It took me months to figure out what that chunk of data represented.

Mod Loader

HLSL Analysis and Assembly Injection

I analyzed the game's pixel shader structure and injected HLSL assembly into a shader variant to blend between two textures in-game.

Code Logic: The patch uses A general-purpose DirectX 11 modding tool. (bo3b/3Dmigoto on GitHub). It matches pixel shader assembly that samples from texture register t0 and binds the previous texture to t50. When the textures have matching dimensions, a frame counter drives a 60-frame blend from the previous texture to the new one.
